为什么这样设计：稳定前缀 × KV-Cache

提示词如此分层，很大程度是在为一个工程目标服务：让可复用的前缀尽量稳定，从而最大化 LLM KV-Cache 的命中。

依据：system-prompt README 的 Token / KV Cache 影响章节。

一条前缀在什么时候“作废”？

只要身份、persona、变量、段文本与顺序的渲染完全相同，system 前缀就保持稳定。任何一处变更——变量插出不同的值、段文本改一个字、schema 重排——都会从第一个变化的 token 起使整个后续缓存失效。这就是为什么：

排序用字典序同号段按 code-unit 字典序而非 locale 排——locale 随机器变，字典序不变，渲染结果跨机器字节级一致。
档位稀疏预留第一方段位 −1000…9900 相邻差 ≥10：新插件插进中间不挤动别人的位置，旧前缀的段序列不变。
PTC 声明确定性PTC 模式的工具声明按工具名字典序渲染，同一工具集每次输出字节级一致。
schema 每次克隆assemble 对工具参数做 structuredClone——“单步内的变更不泄漏到未来装配”，防止某一步的临时改动污染后续前缀。

“稳态的进 system，瞬态的走 user 尾部”

身份/人格/段渲染完全相同时，system 前缀稳定 → 前缀 cache 复用。这是全书所有分层决定的总原则。
沙箱/审批把易变事实做成消息尾部快照，切换时不动前缀、只在尾部新增/替换一小段（第 06 章的机制）。
工具 schema只要可见集合与顺序不变即稳定；限制某 agent 的工具可移除其全部 schema 成本，重排序只改缓存形状不改语义。
AGENTS.md放 user 消息而非 system：项目规则会随文件变，放 system 里每次改文件都毁前缀；放历史里只追加增量。
成本视角小结：启用身份段是每次请求的固定成本；persona 与插件文本随渲染内容增长；schema token 每请求重复。DSH 的对策不是“少说话”，而是“把会变的挪出前缀，把不变的钉死”——连“严格插值宁可抛错”都是防患：畸形提示词会让整段前缀作废，不如首轮就暴露。
