核心心法：一个注册表，一条装配流水线

在 DSH 里，任何想“对模型说一句话”的插件，都不直接拼字符串，而是往 ctx.systemPrompt 这个注册表里“报名登记”。真正把话拼给模型的工作，统一交给 assemble() → renderPrompt() 这条流水线。

本章对应源码：packages/core/system-prompt · packages/core/agent-loop

① 登记（任何时候、任意插件）

工具包、沙箱策略、审批服务、文件引用……各自在加载时调用注册 API，声明“我想在系统提示词的哪一档位、说一段什么话”。登记是一次性的；能不能生效、说成什么样，取决于调用方所在的作用域（第 03 章）与装配时的动态状态。

// 任意插件，贡献一段「有序提示词段」
ctx.systemPrompt.section({
  name: 'tool:bash',
  order: 1000,            // 档位：决定它排在第几段
  text: 'Prefer bash for file & process ops.',
})

② 装配（每个 step 一次）

agent 每次要发请求前，调用 systemPrompt.assemble()：合并全局层与该作用域层 → 按数值顺序排好段 → 求值每个变量与动态上下文 → 跑一个可拦截的 system-prompt/assemble 瀑布 → 返回“四件套”（第 02 章）。随后 renderPrompt() 把段拼成 system 文本，工具 schema 作为独立 wire 字段发给模型。

// packages/core/agent-loop/src/agent.ts
const assembly = await loopCtx.systemPrompt
  .assemble(assembleContextFor(this, signal));
...
const system = renderPrompt(assembly); // 最终 system 文本
关键设计：「登记」和「生效」被刻意拆开。这让 DSH 的提示词像一个可插拔总线的下游：任何插件都能贡献一段，而排序、遮蔽、拦截、变量插值都集中在装配点统一处理——这正是“一切皆插件 + Cordis 事件流水线”哲学的缩影。

流水线上的四道工序

合并merge
全局层 + 请求作用域的层合并；作用域同名项遮蔽全局（第 03 章）。变量也按“离得越近越优先”解析。
▼
排序order
段按 order 升序，同号再按名称的 code-unit 字典序——保证任何机器上结果一致。第一方段位稀疏预留（−1000 ~ 9900，相邻差 ≥10），外部插件插进来不挤动别人。
▼
求值evaluate
静态文本直接用；函数文本在每次装配时重新求值——这是“提示词能跟着运行状态变”的关键机制（第 06 章）。
▼
拦截waterfall
system-prompt/assemble 瀑布事件：任何监听者可在交付前审查/改写装配结果；返回值是权威的。唯一例外：complete 段在瀑布后恢复原样（第 02 章）。
