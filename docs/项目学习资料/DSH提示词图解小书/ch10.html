模式差异：标准 / PTC / Plan / 沙箱 / 审批

DSH 的“模式”分好几层，互不冲突：工具呈现模式（工具怎么给模型）、Plan 模式（先计划后动手）、沙箱模式（文件能写到哪）、审批策略（危险动作问不问人）。每种模式本质上都是“换一段注入的提示词”。

本章对应源码：core/tools（native/ptc/both）· plan/plan-mode · sandbox/sandbox-policy · interaction/user-approval

工具呈现模式：native / ptc / both —— 差别最大的一种

native（默认）

所有工具以 JSON schema 走 tools wire 字段，模型直接发起工具调用。tools:sdk 段返回空。你平时用的就是这个。

ptc

Programmatic Tool Calling：模型只能直接调用 run_code 一个工具，其余工具以 TypeScript/Python 类型声明的形式写进 system，在代码里 await tools.name(args) 调用。多次工具调用合并成一次模型调用，中间结果不进历史。

both

两种呈现并存：wire schema 照发，SDK 声明段也注入。适合过渡期或需要对比评测的场景。可由部署默认或 presentAs() 按作用域声明。

PTC 模式注入的两段关键文本

// ptc 段（order 800，在工具指引之前）：
`run_code` is the only tool you can call directly — a tool call naming any
other tool fails. Reach every tool the SDK declares below from inside the program.

// tools:sdk 段（order 5000）：把全部工具渲染成 TS 声明
interface ToolArgsMap  { read: {file_path: string, ...}; ... }
interface ToolOutputMap{ read: {...}; ... }
type ToolName = keyof ToolOutputMap
declare const tools: { [K in ToolName]: (args: ToolArgsMap[K]) => Promise<ToolOutputMap[K]> }

声明由 renderToolsSdk（TS）/ renderToolsSdkPy（Python）生成，工具按字典序输出、结果字节级确定——同一工具集每次渲染完全一致（第 07 章）。两套语言文案配对维护，防止“TS 的 schema 配 Python 的 SDK”这种错位。模型还能得到 bash 用法示例（run_code({ code: "return await tools.bash({...})" ...})）。PTC 段特意排在工具指引之前——模型先读到“哪些工具能调”，再读到“每个工具是干嘛的”。

模式档位注入方式注入内容要点
Plan 模式开 / 关（/plan 切换）plan:policy 段，条件渲染文本由部署方 config 提供（{ section }，非空校验，未知键报错）；开关状态从 plan/mode 事件折叠得出，未激活返回空段。

子代理普通 / 后台 / 结构化child 作用域：delegation 上下文 + 遮蔽 persona（+ report 段 / structured_output 段）每个 child 独立 scope 互不污染；结构化 child 必须以 structured_output 工具调用收尾，纯文本不算结果。
团队Lead / 成员角色team:policy 作用域段策略 + “你的角色/名字/Team id”；只有 Lead 能 spawn_teammate。
统一心法：在 DSH 里“切换模式”几乎从不重写提示词——它只是让某些段变空、让某些快照换词。模式开关是数据（事件折叠 / config 求值），提示词是这些数据的纯函数投影。这就是为什么任何模式切换都不破坏 system 前缀缓存（第 07 章）。
