一次真实请求的解剖：消息堆栈

把阶段 2/3/4 摊开，一个 step 实际发给模型的请求大致长这样——system 是系统提示词，其余按角色进消息历史。

顺序依据：agent-loop/src/agent.ts 的 preStep/step + agent-instructions 的折入注释。

为什么拆成三条不同的 user 消息？

直接 prompt

生命周期：一次。你说的话，进历史后不再变。它排最前，是这一步的“主线”。

workspace 指令

生命周期：项目级。规则长期有效但随文件变化；来源标记 agent-instructions 让系统能追踪“哪条规则来自哪个文件”、变更是增是删。

runtime 快照

生命周期：一步。“此刻”的沙箱/审批状态；来源标记 form:'snapshot' 附带 sections，可追溯到贡献子系统。

三条 user 消息为何分开？来源不同、生命周期不同：你的话是一次性的；AGENTS.md 是“项目规则、长期但随文件变更”；runtime 快照是“此刻状态、每步重算”。拆开才能各自去重、各自刷新、各自计数，而不是搅成一锅。
一个容易误读的细节：<system-reminder> 虽然名字带 system，但它不是 system 角色——它是一条包着提醒外壳的 user 消息。DSH 用这个外壳告诉模型“这是环境注入的元信息，不是用户在跟你说话”。外壳由生产方（agent-instructions）自行包裹，session 层只投影不加工。
