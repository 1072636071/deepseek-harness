DSH 的「系统提示词」
是怎么一步步注入的

你以为模型收到的是一条固定系统提示词？其实是一座每次对话都在动态搭建的积木塔。 这本小书把注册、分层、组装、运行期再注入的完整链路拆开给你看——所有论断都标注源码出处。

📖 11 章 · 约 25 分钟读完 🔖 基线 dsh 0.1.2-alpha 📅 2026-09-03
第一篇 · 机制篇 —— 拼装的规则
01 核心心法：一个注册表，一条装配流水线

插件只负责“报名登记”，真正拼话给模型的是 assemble() → renderPrompt()。

 02 四种「提示词原料」：段 / 上下文 / 工具 / 变量

一次 assemble 的四件套，各自进入请求的不同部位；还有特供的 complete 人格段。

 03 作用域分层：全局一套，agent 各自遮蔽

为什么不同 agent / 子任务看到的提示词不一样——同名段的“就近优先”规则。
第二篇 · 流转篇 —— 注入的时刻
04 注入全景：从「启动」到「每一步」的五个阶段

阶段 0~4 全景图：越到后面越热闹，运行中的“再注入”才是重头戏。

 05 一次真实请求的解剖：消息堆栈

system、tools、直接 prompt、workspace 指令、runtime 快照在请求里的真实排布。

 06 「运行还会注入」：动态上下文的去重快照

为什么每个 step 都可能冒出新的 "Current runtime context"——变了才注入的投影机制。
第三篇 · 设计篇 —— 为什么这样造
07 设计动机：稳定前缀 × KV-Cache

“稳态的进 system，瞬态的走 user 尾部”——分层注入背后的成本账。

 08 实测：DSH 自带提示词到底啰不啰嗦？

逐段量出来的结论：刻意反啰嗦设计；真正的“大头”另有其人。附精简旋钮清单。
