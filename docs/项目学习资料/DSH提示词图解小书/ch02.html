四种「提示词原料」：段 / 上下文 / 工具 / 变量

一次 assemble() 的返回值 PromptAssembly 有四件套。其中「段」与「工具」进入 system，而「动态上下文」是特殊的——它不进 system，而是被投递成一条独立的 user 角色消息（第 06 章细讲）。

本章对应源码：packages/core/system-prompt/src/index.ts

段 section —— 提示词的正文

带 name/order/text。按 order 升序拼接；同号时再按名称的 code-unit 字典序（保证任何机器上结果一致）。文本可以是静态字符串，也可以是每次装配都重新求值的函数；正文里可写 {{变量}}，由 render 阶段插值。

harness:identity        order -1000
harness:source          order -900
web-surface             order -800
deployment:persona      order 0
plan:policy             order 500
tool:bash / tool:pwsh   order 1000/1010
tool:read / write/edit  order 1100...
tools:sdk (PTC)         order 5000
deliverable-files       order 9000
structured-output       order 9900

↑ 仓库内第一方档位用 FIRST_PARTY_SECTION_ORDER 稀疏预留（相邻差 ≥10），外部插件可用任意有限 order。

上下文 context —— 运行时“事实快照”

也是 name/order/text，但不进 system。它描述“当前这一时刻”的可变事实（当前沙箱模式、当前审批策略……），由拥有该事实的插件注册，每次装配现算。

sandbox:policy    order 110  // 当前 sandbox 模式
approval:policy   order 115  // 当前审批策略
subagent:delegation order 120 // 子代理接到的任务

求值为空文本的 context 不产生任何输出——“事实消失了”就等于“这句话从没说过”。

工具 tools —— 模型能做什么

工具 schema 提供方每次装配时求值，产出模型可见的 ToolSchema[]。大多数工具包让自己的 ToolRuntime 自动注册，无需手动接线。可配置的 toolOrder 决定面向模型的工具排序，其中 <unlisted-tools> 是“其余工具插这里”的占位符（有且只能有一个）。

为什么工具也算“提示词的一部分”？对模型而言“知道自己能做什么”和“知道自己该怎么做”是连贯的，所以 assemble() 把二者作为一个整体交付——尽管发给模型时 schema 是独立 wire 字段。

变量 variable —— 正文里的活引用

以 {{name}} 出现在段文本里，render 时严格插值。agent-loop 循环层提供 provider/model/cwd，任何插件都能注册自己的“事实”。

ctx.systemPrompt.variable('cwd',
  ({ agent }) => agent?.session.header.cwd);
// 段正文可写：当前工作目录为 {{cwd}}
严格规则：未注册的、已注册但当前无值的、或畸形 {{…}} 引用都会让渲染直接抛错。DSH 认为“提示词拼错”比“静默出错”更好——畸形提示词会毁掉整段前缀缓存（第 07 章）。

还有一种「特供」：complete 人格段

任一段可声明 complete: true，表示“不要其他任何段，就用我说的这句当整条系统提示词”。装配仍会跑完（好让工具/上下文/变量可解析），随后这段被恢复为唯一的提示词段。同时存在多个有效 complete 段会导致装配失败。

render 的两条铁律

去空段求值为空的段在 renderPrompt() 里被过滤，剩余段用空行连接。“条件段”就是靠返回空串实现隐身的——这是全书最重要的机制之一（第 06、10 章反复出现）。
严格插值{{…}} 只按已注册变量解析：未知名、有注册无值、畸形组全部抛错；孤立的 {{（后面没有 }}）视为字面文本；替换进去的值不再二次扫描。
本章心法：记住“静态正文 + 活的事实 + 能力清单 + 变量”四件套的分工。后面所有模式与阶段差异，本质上都是这四种原料在不同条件下的取值变化。
